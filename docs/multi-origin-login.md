# 多网络入口与钉钉登录

本机配置允许以下回调，服务监听 `0.0.0.0:5020`：

| 网络 | 控制台入口 | 回调 |
| --- | --- | --- |
| 当前局域网 | `http://192.168.1.4:5020/` | `http://192.168.1.4:5020/auth/dingtalk/callback` |
| Tailscale | `http://100.73.136.41:5020/` | `http://100.73.136.41:5020/auth/dingtalk/callback` |
| 办公网 | `http://172.16.37.247:5020/` | `http://172.16.37.247:5020/auth/dingtalk/callback` |

用户应打开控制台入口，而不是直接打开没有 state/authCode 的回调。每个 IP 使用独立的浏览器会话，需要分别登录，不共享 Cookie。

## 配置

`.env` 中 `DINGTALK_REDIRECT_URI` 保留原单入口；`DINGTALK_REDIRECT_URIS` 添加逗号分隔的额外回调。两者合并形成明确白名单。授权始终选择当前请求同源的已配置回调，未登记的 Host 拒绝发起授权，不使用转发头推导回调。

钉钉应用后台也必须登记对应回调。不能覆盖这个共用应用已有的其它系统回调。2026-11-04 通过已登录浏览器核对，三个回调均已存在，未改写后台设置。LAN 与 Tailscale 均已观察到正式服务已登录首页；办公网待网络恢复后验收，不能用健康检查代替真实登录。

## 网络边界

2026-11-04 本机网卡实际地址为 `192.168.1.4` 与 `100.73.136.41`，两者 healthz 可达。`172.16.37.247` 当时不在本机网卡上，需连接对应办公网络并取得该地址，或由网络管理员提供合法路由后才能访问。不会通过添加未经确认的 IP 别名模拟可达。

Tailscale 入口需要客户端已接入同一 tailnet，且 ACL 允许 TCP 5020。HTTP 入口未提供 TLS；生产或不可信网络应在单独设计并确认的 HTTPS 入口上使用。

## 更新后

先运行 `rtk .venv/bin/python -m pytest`，再执行 `rtk deploy/restart.sh` 并检查健康状态。验证每个 `/auth/dingtalk/begin` 的 `redirect_uri` 与访问来源一致，再由白名单用户分别完成钉钉登录。
