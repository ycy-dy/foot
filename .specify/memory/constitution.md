## Core Principles

### I. 现行政策与70%证据门槛（NON-NEGOTIABLE）
用户后续明确确认沿用删除前最终推荐要求并新增证据可信度>=70%硬门槛，授权代码实现与启动。现行契约在规格014的policy.md/policy.yaml/scoring.md，不恢复旧V6文件或编辑器。缺可靠评分、不足70或硬冲突不推荐，覆盖旧条件票必出。评分不是命中概率，真实AI决策、审核人工发布、冻结每日台账与次日复盘不可绕过。计划和通知默认仍停用，需单独授权。

### II. 真实数据、不编造
赛程、赔率、在售状态、首发、概率和赛果只能来自可追溯来源或已运行模型；缺失时显示“待核/不可用/null”。运行工件是历史资料，不能重新授权业务政策。

### III. 研究与展示，不投注
系统不接入投注、支付或下单接口，不追损加码，页面和推送不得承诺命中或收益。实际投注金额与返还字段固定为 null。

### IV. 历史冻结、版本可追溯
已存在的报告、快照、台账和运行工件不覆盖、不伪造成功；本次文档整理不删除或改写 `runs/`、`ledger/`、`var/`。`history/` 已按用户确认删除，不能自动恢复。

### V. 测试先行、小步可回退
每个新功能先有规格（`specs/NNN-*/spec.md`），再有计划和任务。改动应带自动化测试；外部依赖一律可模拟。文档改动验证链接与差异即可，不宣称运行时测试或部署完成。

### VI. 安全与最小权限
密钥只放 `.env`（权限600、git 忽略），不写进代码、日志或文档。仅白名单用户可登录，角色分为 admin 和 viewer。审计记录登录、拒绝和受控操作；Agent 子进程只给完成任务所需权限。

### VII. 真实 AI 决策与确定性边界
只有规格013或其后新的用户确认规格明确授权后，赛前研究、推荐取舍与复盘归因才可使用真实 AI；程序负责事实核验和确定性计算，不以模板或机械选项冒充 AI。AI 不能绕过审核、改原票或改变确定性结算。保存输入、原始返回、验证与哈希；双失败不得伪造成功。

## 技术约束

- Python ≥3.12，Flask、SQLite、gunicorn；src 布局，包名为 `foot_web`；依赖写在 `pyproject.toml`，用 uv 管理 `.venv`。
- 分层依赖方向：core → storage → data → services → engine/scheduler/notify → auth/web；下层不得反向依赖上层。
- 金额、赔率和乘积用 Decimal 计算；具体业务阈值、玩法和维度须等待规格013，不得从已删除体系恢复。

## 开发流程

1. `/speckit-specify` 写规格013（或后续用户确认规格）→ `/speckit-clarify`（可选）→ `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement`。
2. 各阶段按规格要求运行测试，结果如实写入 tasks.md；本次文档整理不运行全量测试。
3. 目录或路径变更须同步 `docs/directory-layout.md`；跨目录移动须生成迁移对照表。
4. 阅读治理地图、系统蓝图和现有规格时，旧规格只作历史实现记录，不视为当前业务授权。不得恢复已删除体系或 `history/`。
5. 规格完成、实现完成、测试通过、真实验收和部署完成分别记录；不把文档修改或旧工件存在宣称为运行时完成。

## Governance

本宪法高于其他开发惯例，但低于系统/开发者指令、用户直接指令和 `AGENTS.md`。修订须写明理由、版本号和生效日期，并检查受影响规格与模板。增加复杂度应在 plan.md 的 Complexity Tracking 中说明理由。
